# 2차 개발 확장 — 분담

> 상태: 진행중 · 갱신 2026-09-10 · 관련: [1차 분담](1차_구현_분담.md), [설계 결정](설계_결정.md), [개발 환경](개발_환경.md)
> 무엇: 기획 「26.9.6 개발 확장」의 구현 순서 2~9단계를 기존 A·B 두 갈래에 이어서 가른 것과, 이번에 새로 생기는 계약 네 개.

**표기** — `(+9/7)` 처럼 붙은 것은 그날 추가·변경된 항목이다. 날짜 없는 줄은 최초 작성분(9/7)이다.

원본 기획: `26.9.6 개발 확장.pdf` (카카오톡 수신, 11쪽). 이 문서는 그중 **프로그래머 몫만** 다룬다.

## 0. 먼저 — 이번 차수는 1차와 조건이 다르다

1차는 "서로의 파일을 3주 동안 안 열고 짜다가 마지막에 합친다"가 전제였다. 지금은 아니다.
**코드가 이미 돌고 있고, 2차 기능 대부분이 기존 시스템에 붙는다.** 그래서 가르는 기준이
1차의 "의존성"에서 한 겹 더 들어간다 — **누가 그 데이터의 원본을 쥐고 있는가**로 가른다.

기획 문서가 스스로 그어놓은 선이 그대로 쓸 만하다.

> 자유 플레이 → **영업 시작 → 영업 진행 → 영업 종료** → 정산 → 자유 플레이 복귀

**영업 타이머가 도는 동안이 B, 그 바깥이 A다.** 1차와 같은 선인데, 1차엔 "바깥"에
농사밖에 없어서 안 보였을 뿐이다. 2차에 바깥이 크게 늘어난다 — 월드 시간, 창고,
시설 업그레이드, 오늘의 메뉴, 탐사정.

## 1. 단계별로 누구 것인가

기획의 「구현 순서」 번호를 그대로 쓴다. 회색(8·9단계)은 기획이 후순위로 내린 것이다.

| 단계 | 무엇 | 담당 | 왜 |
|---|---|---|---|
| **2단계 잔여** | 완성 요리 오브젝트 생성 | **B** | 요리 시스템 안쪽이다 |
| | 판매 및 정산 | **B**(집계) + **A**(골드 반영) | 아래 계약 5 |
| **3단계** | 영업 시스템 (시작/시간/종료/정산 전달) | **B** | `DayPhase`를 B가 준다 — 1차 계약 3 |
| **4단계** | 월드 시스템 (시간 흐름·환경·파라미터) | **A** | 씬·조명·환경이 A 쪽이다. 아래 계약 6 |
| **5단계** | 요리 메뉴 추가 · 미니게임 2종 · 손님 유형 | **B** | 설계 결정 11 — 미니게임은 통째로 B |
| | 오늘의 메뉴 | **A** | 의존이 전부 A쪽이다. 아래 계약 7 |
| **6단계** | 자원 운용 (창고·보급품 상자·특수 자원) | **A** | `Warehouse`가 이미 A 소유다 |
| | └ 요리 전 재료 확인·차감 | **B** | `Has`/`Consume` 그대로. 다만 **닿는 경로가 바뀌었다** `(+9/9)` — 아래 ⚠️ |
| **7단계** | 시설 업그레이드 | **A** | 골드를 쓰는 성장이다. 아래 계약 8 |
| **8단계** *(후순위)* | 탐사정 · 특수 자원 · 상위 업그레이드 | **A** | 필드·경제·성장 계열 전부 |
| **9단계** *(후순위)* | 낚시 · 농사 · 탐사 확장 | **A** | 1차부터 농사는 A였다 |

한 줄로: **A는 「영업을 준비하고 그 결과로 성장하는 쪽」, B는 「영업 3분 동안 일어나는 일」.**

## 4. 새 계약 네 개

1차의 계약 4개(`IngredientData`/`MenuData`, `IInteractable`/`Warehouse`,
`DayPhase`/`GameManager`, `ServeBoard`/`ServeTask`)는 **그대로 유효하다.** 여기 넷이 는다.

> **`(+9/10)` 계약 4(`ServeBoard`/`ServeTask`)는 더 이상 유효하지 않다.** 이슈 #33 에서
> 뒤집었다 — `ServeTask` 와 `ServeBoard.Post()` 가 **삭제**됐고, B가 보드를 부르는 일이
> 없어졌다. 대신 B가 `CookingCounter.CountOf` / `TryTakeFood` 를 열어준다(방향이 B→A로 역전).
> 왜 그렇게 갔는지는 [설계 결정 9](설계_결정.md) 의 `(+9/10)` 항을 볼 것.

넷 다 **A가 주고 B가 읽기만 한다.** B가 A의 상태를 바꾸는 건 계약 5 하나뿐이다.

⚠️ **1차 계약 2가 하나 바뀌었다 `(+9/9)`.** `Warehouse` 가 `IInteractor` 에서 빠졌다.

```csharp
// B가 재료를 보는 법 — actor.Warehouse 가 아니다
if (!Warehouse.Instance.Has(menu.Recipe)) return;   // 부족 → 선택 불가 표시
Warehouse.Instance.Consume(menu.Recipe);            // 차감 후 미니게임 시작
```

**바뀐 게 둘이다** — 닿는 경로(`Warehouse.Instance`)와, `Has`/`Consume` 의 인자(`MenuData` → `IReadOnlyList<RecipeEntry>`).
`menu.Recipe` 가 이미 그 타입이라 변환은 없다. `Add` 는 그대로다. 같은 재료가 여러 줄로 들어오면 합쳐서 본다.
근거는 기획 「8. 자원 관리」의 「플레이어가 식재료를 직접 들고 이동하지 않는다」 ·
「요리 시스템에서도 동일한 식재료 보유 데이터를 참조한다」. 설계 결정 6·10 참고.

### 계약 5. 지갑 — A가 주고, B가 정산 때 한 번 넣는다

```csharp
namespace Marea.Economy
{
    public class Wallet : MonoBehaviour
    {
        public int Gold { get; private set; }
        public event Action<int> OnGoldChanged;

        public void Add(int amount);            // B가 정산에서 부른다
        public bool TrySpend(int amount);       // A만 부른다 (업그레이드)
    }
}
```

- **B가 부르는 건 `Add()` 한 줄이다.** 영업 정산이 끝나면 총 매출을 넣는다.
- `TrySpend()` 는 A만 쓴다. 부족하면 `false` — 던지지 않는다. 버튼 비활성화가 UI 몫이라
  실패가 예외 상황이 아니다.
- **`Add()` 는 정산 확정 시점에 딱 한 번 부른다.** 음식 하나 팔 때마다 부르지 않는다.
  중간에 영업이 끊기면 어디까지 들어갔는지가 애매해진다.

> **코드가 됐다 `(+9/10)`.** `Economy/Wallet.cs`. 시그니처는 위 그대로고, 씬 오브젝트
> `Wallet` 에 `Instance` 로 노출한다(`Warehouse` 와 같은 방식). 실패 처리 셋을 정했다 —
> `Add(0)` 은 조용히 통과(**매출 0인 날은 정상이다**), `Add(음수)` 는 `LogError` 후 무시
> (조용히 빼주면 `TrySpend` 의 잔액 검사를 우회하는 두 번째 경로가 생긴다),
> `TrySpend(0 이하)` 는 `LogError` + `false`.
>
> ⚠️ **`Add()` 의 호출처가 아직 0개다.** B가 정산 확정에 한 줄을 붙이기 전까지 골드는
> `[ContextMenu] 테스트: +1000G` 로만 는다. **금액에 `SettlementBonus` 를 곱한 뒤 넣는다.**
>
> ```csharp
> Wallet.Instance.Add(Mathf.RoundToInt(TodaySales.totalRevenue * FacilityLevels.Instance.SettlementBonus));
> ```
>
> **저장·로드는 없다.** 씬을 다시 켜면 `startingGold` 로 돌아간다. 별도 이슈다.

### 계약 6. 월드 시계 — A가 주고 B가 읽는다

```csharp
namespace Marea.World
{
    public enum TimeSlot { Day, Evening, Night, Dawn }   // (+9/8) Morning → Dawn

    public class WorldClock : MonoBehaviour
    {
        public static WorldClock Instance { get; private set; }
        public TimeSlot Slot { get; }
        public float NormalizedTime { get; }        // 0~1, 하루 안에서의 위치
        public float Hour { get; }                  // (+9/8) 0~24, 게임 내 시각
        public event Action<TimeSlot> OnSlotChanged;
    }
}
```

- **`Morning` → `Dawn` 으로 바꿨다 `(+9/8)`.** 기획이 말하는 네 번째 시간대가 아침이
  아니라 **새벽**이라 이름이 어긋나 있었다. **B가 읽는 값이므로 계약 변경이다** — B가
  아직 `GameManager` 를 안 짰을 때 바꾼다. 순서도 낮 → 저녁 → 밤 → 새벽 으로 맞췄다.
- **월드 시간은 영업 가능 여부를 제한하지 않는다**(기획 명시). B는 `Slot` 을 읽어
  손님 유형 확률만 조정한다. 영업 시작을 막는 데 쓰지 않는다.
- B가 읽는 건 `Slot` 뿐이다. `NormalizedTime` 은 A의 조명이 쓴다.
- **시간대 경계는 4등분이 아니다 `(+9/8)`.** 낮 06~16 / 저녁 16~20 / 밤 20~04 / 새벽 04~06
  이 기본값이고 인스펙터에서 조절한다. **밤만 자정을 넘어간다.** 하루 길이 기본 24분.
- **`OnSlotChanged` 는 시작할 때 쏘지 않는다 `(+9/8)`.** 하루에 정확히 네 번이다.
  늦게 켜진 구독자는 `Slot` 을 직접 읽어 초기 상태를 맞춘다.
- **`DontDestroyOnLoad` 를 붙이지 않았다 `(+9/8)`.** 프로젝트에 `SceneManager.LoadScene`
  이 아직 한 군데도 없어서 지금은 하는 일이 없고, 씬 전환이 생기면 살아남아야 하는 건
  이 숫자들이지 씬 참조를 든 조명 쪽이 아니다.
- 현재 단계에서는 **조명·환경 변화까지만 구현**하고 시간대별 파라미터는 값을 노출만
  해둔다(기획 명시). B가 실제로 확률을 갈라 쓰는 건 그다음이다.

### 계약 7. 오늘의 메뉴 — A가 주고 B가 읽는다

```csharp
namespace Marea.Economy
{
    public class TodayMenu : MonoBehaviour
    {
        public IReadOnlyList<MenuData> Selected { get; }   // 이번 영업에 팔 메뉴
        public int MaxCount { get; }                       // 시설 레벨로 늘어난다
        public event Action OnConfirmed;
    }
}
```

- **B는 `Selected` 안에서만 주문을 만든다.** 여기 없는 메뉴는 주문으로 생성하지 않는다.
- **선택은 영업 시작 전에만 가능하다.** 영업 중에는 A가 UI를 잠근다 — `DayPhase` 로 판단한다.
- `Selected` 는 영업 중에 바뀌지 않는다. B는 영업 시작 시점에 한 번만 읽어도 된다.

> **왜 오늘의 메뉴가 A인가.** 이게 이번 분담에서 유일하게 이상해 보이는 자리라 근거를 남긴다.
> 이 기능이 하는 일은 「해금 목록 조회 → 보유 재료 대조 → 상한 안에서 고르기 → 확정」이다.
> 네 개 중 **셋이 A의 데이터**다 — 해금은 시설 업그레이드(A), 보유 재료는 창고(A),
> 상한은 시설 레벨(A). B에게 주면 계약이 세 개 늘어난다.
> B가 필요로 하는 건 마지막 `Selected` 목록 하나뿐이다. **의존이 무거운 쪽에 붙인다.**

### 계약 8. 시설 레벨 — A가 주고 B가 읽는다

```csharp
namespace Marea.Economy
{
    public enum FacilityKind { Business, Kitchen, Storage }

    public class FacilityLevels : MonoBehaviour
    {
        public static FacilityLevels Instance { get; private set; }
        public int LevelOf(FacilityKind kind);
        public float BusinessDuration { get; }   // 영업 시간 (초). B의 타이머가 읽는다
        public float SettlementBonus { get; }    // 정산 배수 (1.0 = 보너스 없음)
    }
}
```

- **B는 원시 레벨을 해석하지 않는다.** `BusinessDuration` `SettlementBonus` 처럼
  **이미 계산된 값**을 읽는다. "영업 시설 2레벨이면 몇 초인가"는 A 안에서 끝난다.
  레벨이 3단계로 늘든 곡선이 바뀌든 B는 안 고친다.
- 기획의 「영업 시설 → 영업 시간 증가 / 정산 금액 3% 추가」가 정확히 이 두 값이다.
- 효과가 늘면 프로퍼티가 는다. **`FacilityKind` 에 값을 추가하는 건 A 마음대로 해도 되지만,
  프로퍼티를 지우거나 이름을 바꾸는 건 B에게 먼저 말한다.**

> **코드가 됐다 `(+9/10)`.** `Economy/FacilityLevels.cs` + `Economy/FacilityKind.cs`
> (enum을 따로 뺐다 — `Data/FacilityData.cs` 가 참조해야 하는데 `FacilityLevels` 보다 먼저
> 생겼다). 계약 넷은 위 그대로고, **A 전용으로 셋을 더 얹었다** — 프로퍼티를 늘리는 건
> A 마음대로라는 위 규칙에 따른 것이라 B는 안 봐도 된다.
>
> ```csharp
> public FacilityData DataOf(FacilityKind kind);   // 목록 UI가 이름·비용을 꺼낸다
> public bool CanRaise(FacilityKind kind);         // 최대 단계 판정
> public bool TryRaiseLevel(FacilityKind kind);    // 골드는 안 본다 — FacilityUpgrade가 먼저 뺀다
> ```
>
> **레벨→값 계산은 전부 여기서 끝난다.** 레벨별 수치는 `Data/FacilityData.cs` 에셋에 있고
> (설계 결정 13), 영업 시설만 효과표를 갖는다 — 주방·창고는 기획이 효과를 확정하기 전까지
> **레벨만 오르고 값은 안 내준다.** UI에는 「효과 미정」으로 뜬다.
>
> ⚠️ **B가 아직 안 읽고 있다.** 값은 실제로 바뀌는데(실측: lv1→4 에서 180→360초,
> 1.00→1.09배) 쓰는 쪽이 없다. B가 붙일 한 줄:
>
> ```csharp
> // BusinessManager.cs:49  private float businessDuration = 180f;  를 이걸로
> FacilityLevels.Instance.BusinessDuration
> ```
>
> **저장·로드는 없다.** 씬을 다시 켜면 전부 1레벨이다.

## 5. 왜 이렇게 갈랐나

- **영업 타이머 안쪽이 B, 바깥이 A.** 1차의 선을 그대로 늘렸다. 2차에서 새로 생기는 것
  대부분이 "영업 전 준비"거나 "영업 후 성장"이라 자연스럽게 A로 온다.
- **정산은 쪼갠다 — 집계는 B, 골드는 A.** 무엇을 얼마에 팔았는지는 주문을 쥔 B만 안다.
  골드 잔액은 업그레이드·고용이 다 보는 값이라 A가 원본을 쥔다. 경계는 `Wallet.Add(int)`
  한 줄뿐이라 넓지 않다.
- **미니게임 2종은 통째로 B.** 설계 결정 11에서 미니게임 입력 에셋을 B로 갈라놨다.
  A가 하나 가져가면 그 결정이 무너지고 `.inputactions` 가 세 벌이 된다.
  둘 다 입력이 단순하다 — 생선 구이는 클릭 1회, 스튜는 방향 입력뿐이다.
- **월드 시스템은 A.** 조명·스카이박스·환경은 씬을 만지는 일이고 아트와 직접 붙는다.
  B가 가져가면 영업 루프를 짜다 말고 씬을 열게 된다.
- **B에게 파라미터 계산을 넘기지 않는다.** 계약 8이 그것이다. 밸런스 수치는 전부
  기획이 나중에 확정한다(기획 문서가 다섯 군데에서 "이후 밸런스 단계에서 확정"이라고 적었다).
  그 수치가 흔들릴 때 **한쪽만 고치면 되게** 계산을 A 안에 가둔다.
- **8·9단계는 전부 A지만 지금 안 짠다.** 기획이 회색으로 내렸다. 방향만 못박아둔다 —
  탐사정·낚시·농사가 나중에 B로 넘어가는 일은 없다.

## 6. 진행 순서

단계 번호가 곧 순서다. 다만 **A와 B가 같은 단계를 동시에 잡지는 않는다.**

| | A | B | 끝나면 |
|---|---|---|---|
| **1** | `Wallet` 껍데기 커밋 | **`GameManager`·`DayPhase` 커밋 (최우선)** | A가 영업 상태를 읽을 수 있다 |
| **2** | `WorldClock` **커밋됨 `(+9/8)`** · 조명 전환은 아트 대기로 보류 (4단계) | 영업 시작·타이머·종료 (3단계) | 영업이 3분 돌고 끝난다 |
| **3** | 보급품 상자 · 창고 UI (6단계) **끝 `(+9/9)`** | 판매·매출·정산 화면 (2·5단계) | 하루가 매출로 닫힌다 |
| **4** | `FacilityLevels` · 업그레이드 UI (7단계) | 미니게임 2종 · 메뉴 추가 (5단계) | 번 돈으로 시설이 오른다 |
| **5** | `TodayMenu` · 선택 UI (5단계) | 주문을 오늘의 메뉴로 제한 · 손님 유형 | 무엇을 팔지 고르게 된다 |
| **6** | 특수 자원 · 탐사정 (8단계) | 밸런스 반영 | 후순위 구간 |

**1행은 병렬이 아니다.** B의 `GameManager` 가 나오기 전에는 A가 "영업 중이면 UI를 잠근다"를
짤 수 없다. A는 그동안 `Wallet` 과 `WorldClock` 처럼 상태를 안 보는 것부터 잡는다.

## 8. 미해결

- **미니게임 종류가 기획과 코드에서 다르다.** 기획 문서 7장은 **생선 구이 + 스튜** 2종인데,
  구현된 건 **꼬치**고 `CookingMenuUI` 카테고리는 **꼬치·스튜·스테이크** 3종이다.
  꼬치를 남기고 2종을 더하면 3종, 기획대로면 2종이다. **기획에 물어야 한다.**
- **요리대 점유** (1차에서 넘어온 것) — 완성품이 요리대에 놓이고 직원이 가지러 오는데,
  그 전에 다음 요리를 시작할 수 있나. 메뉴가 늘고 영업 시간이 3분으로 고정되면
  여기가 병목이 된다. 「주방 업그레이드」가 이걸 푸는 자리일 수 있다. B 영역.
- **영업 종료 시 큐에 남은 `ServeTask`.** 기획은 「배달 중인 음식은 전달하고 종료」,
  「대기 중 음식은 제거」다. 지금 `ServeBoard` 에는 **큐를 비우는 함수가 없다.**
  A가 `ServeBoard.Clear()` 를 열어줘야 한다 — 계약 4의 확장이므로 B에게 말하고 넣는다.
- **미니게임 중에도 영업 타이머는 감소한다**(기획 명시). 플레이어는 `BeginBusy()` 로
  잠기지만 타이머와 직원은 계속 돈다. 1차 미해결로 남겨둔 「미니게임 중에도 직원은
  돌아야 한다」와 같은 자리다. 3단계 끝나면 한 번 같이 돌려본다.
- **`Wallet` 을 씬 오브젝트로 둘지 정적으로 둘지.** `WorldClock`·`FacilityLevels` 는
  `Instance` 를 적어뒀지만 `Wallet` 은 안 적었다. 셋 다 씬에 하나뿐인 물건이라
  같은 방식으로 가는 게 맞다. 1차의 `ServingStaff` 때처럼 **싱글턴을 나중에 못 걷어내는
  일**이 생기지 않는지 A가 먼저 본다.
- **밸런스 수치 전부.** 영업 시간, 판정 구간, 업그레이드 비용, 메뉴 가격, 시간대 보정 —
  기획 문서가 다섯 군데에서 "이후 밸런스 단계에서 확정"이라고 적었다.
  전부 `[SerializeField]` 나 SO로 빼두고 코드에 숫자를 박지 않는다.
