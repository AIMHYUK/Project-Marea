# 설계 결정

> 상태: 진행중 · 갱신 2026-08-31 · 관련: [1차 구현 분담](1차_구현_분담.md), [개발 환경](개발_환경.md)
> 무엇: 왜 이렇게 짰는지와, 어떤 조건이 오면 이 결정이 뒤집히는지.

결정마다 **언제 뒤집히나**를 같이 적는다. 이게 없으면 나중에 조건이 바뀌었는데도
옛 결정을 그대로 지키게 된다.

**표기** — `(+8/31)` 처럼 붙은 것은 그날 추가·변경된 항목이다.
날짜가 없는 줄은 최초 작성분(8/28)이다.

## 1. 상태는 두 개다 — 합치지 않는다

`DayPhase`와 `PlayerState`는 묻는 질문이 다르다.

| | `DayPhase` | `PlayerState` |
|---|---|---|
| 묻는 것 | 지금 **가게**가 뭐 하는 시간인가 | 지금 **캐릭터**가 조작 가능한가 |
| 값 | `Preparing / Open / Closing` | `Idle / Moving / Interacting` |
| 개수 | 씬에 1개 (전역) | 플레이어마다 1개 |
| 바뀌는 주기 | 하루에 3번 | 초 단위로 계속 |
| 공개 범위 | `public` — A가 구독 | `private` — 밖엔 `IsBusy`만 |
| 소유 | B (`GameManager`) | A (`PlayerController`) |

합치면 `준비중+이동중`, `영업중+미니게임`처럼 조합이 곱해져 enum이 12개로 터진다.

**흐름은 단방향이다.**

- OK — 정산 화면이 뜨면 게임 상태가 플레이어 입력을 잠근다
- NO — 플레이어가 밭을 클릭했다고 게임 상태가 바뀐다. 영업 시작은 **버튼**이 바꾼다

`PlayerController`의 상태는 `private`이라 B는 `IsBusy`만 본다. A가 나중에
`Harvesting`을 추가해도 B 코드는 그대로다.

> 뒤집히는 조건: 없음. 축이 다른 두 상태는 어떤 규모에서도 합치지 않는다.

## 2. 손님·밭 상태는 FSM으로 만들지 않는다

- **손님** `Entering → Seated → Ordering → Waiting → Leaving` — `Customer.cs` 안의 enum 필드
- **밭** `Empty → Growing → Harvestable` — `FarmPlot.cs` 안의 enum 필드

1차에서 State 패턴이나 FSM 프레임워크까지 가면 과설계다. `enum + switch`로 시작한다.

> 뒤집히는 조건: 한 오브젝트의 상태가 **6개를 넘으면**, 또는 상태마다 진입/퇴장
> 처리가 길어지면 그때 클래스로 쪼갠다.

## 3. ScriptableObject에는 안 변하는 값만 넣는다

SO는 에셋이라 씬에 몇 개가 놓이든 실체가 하나다. 인스턴스마다 달라야 하는 값이
거기 있으면 전부 공유된다.

| | 어디에 | 예 |
|---|---|---|
| **정의** (안 변함) | ScriptableObject | 감자는 60초 걸린다, 스튜는 1200원이다 |
| **런타임 상태** (변함) | MonoBehaviour 또는 순수 C# 클래스 | 이 밭은 지금 42초째다, 창고에 감자가 3개다 |

MdCalling에서 `Item`(SO) 안에 `private int _stack;`이 남아 있는데, 이건
`InventoryItem`으로 옮기고 남은 잔재다. 같은 실수를 반복하지 않는다.

> 뒤집히는 조건: 없음.

## 4. 재료와 작물은 다른 데이터다

`IngredientData`는 *창고에 쌓이는 것*, `CropData`는 *밭에서 자라는 것*. 1:1이 아니다.

- 밀가루·소금은 재료지만 밭에서 안 자란다 (상점 구매)
- 감자 한 포기에서 감자 여러 개가 나온다 — 수확량은 작물 쪽 정보
- 성장 시간·성장 단계 스프라이트는 재료가 알 필요 없다

```csharp
[CreateAssetMenu(menuName = "Marea/Crop")]
public class CropData : ScriptableObject {
    public IngredientData Harvest { get; }   // 여기서만 참조
    public int HarvestCount { get; }
    public float GrowSeconds { get; }
    public Sprite[] GrowthStages { get; }
}
```

`IngredientData`에 `growSeconds`를 그냥 넣으면 밀가루·소금 에셋에 영영 비는 필드가
남는다. 재료가 20종 되면 인스펙터에서 "이건 심을 수 있나?"를 매번 판단해야 한다.

**분담상 중요한 점: `CropData`는 A만 쓴다.** B는 창고에 재료가 있는지만 알면 된다.
그래서 농사가 확장돼도 공유 지점이 늘지 않는다.
(`(+8/31)` 공유 지점은 이제 4개다. 늘어난 건 농사가 아니라 서빙 직원 때문이다 — 결정 9 참고.)

> 뒤집히는 조건: 없음.

## 5. 공통 베이스 클래스(`IdentifiedObject`)는 지금 두지 않는다

MdCalling은 `IdentifiedObject : ScriptableObject`(id·codeName·icon·Category + Clone +
JSON) 아래에 `Item`·`Location`·`Quest` 등을 두고, `IODatabase`로 중앙 조회한다.

이번엔 안 가져온다.

- 필드가 3~4개뿐이라 상속으로 버는 게 없다
- 무엇보다 **A와 B가 동시에 만지는 파일이 하나 더 생긴다**

> 뒤집히는 조건: **재화·상점이 들어와 재료가 20종을 넘으면.** 그때 MdCalling에서
> `IdentifiedObject` + `IODatabase`를 그대로 떠온다. 이미 검증된 코드다.

## 6. 창고는 `Warehouse`, 인벤토리는 나중에 `Inventory`

이름을 갈라둔다. 둘은 다른 물건이다.

- **`Warehouse`** (1차) — 재료 수량만. `Dictionary<int,int>` 하나로 충분하다
- **`Inventory`** (2차) — 소지품 그리드, 드래그, 회전. MdCalling의 그 인벤토리

1차에서 MVC로 쪼개면 과설계다. **다만 `Has()` / `Consume()` / `Add()` 시그니처만
지금 확정해두면**, 나중에 안을 Model로 갈아끼워도 B의 `CookingStation`은 안 건드린다.

> 뒤집히는 조건: 인벤토리 UI가 들어올 때 `Warehouse` 내부를 `WarehouseModel`(순수
> C# 클래스) + `WarehouseView`로 쪼갠다. 공개 API는 유지한다.

## 7. 인벤토리 UI가 들어와도 상태는 늘리지 않는다 — UI 스택으로 막는다

UI 열림은 **세 번째 축**이다. 가게가 뭐 하는 시간인지도 아니고 캐릭터가 어디쯤인지도
아니다. `PlayerState`에 `Inventory`를 넣으면 닫을 때 원래 상태로 되돌려야 하고,
이동 중·밭 앞·대기 중 어디서든 열리므로 덮어쓰기가 아니라 **얹기**가 된다.

```csharp
public static class UIStack {
    public static bool BlocksGameplay { get; }   // 블로킹 패널이 하나라도 열려 있나
    public static void Push(IPanel p);
    public static void PopTop();                 // ESC 한 번에 맨 위 하나만
}
```

`PlayerController`에는 게이트 한 줄만 늘어난다.

```csharp
if (GameManager.Instance.Phase == DayPhase.Closing) return;
if (UIStack.BlocksGameplay) return;   // 2차에 추가
```

`bool isInventoryOpen` 하나로 안 되는 이유는 **쌓이기 때문**이다. 인벤토리 → 아이템
상세 → "버리시겠습니까?" 에서 ESC를 누르면 확인창만 닫혀야 한다.

A(창고 UI)와 B(주문·정산 UI)가 같이 쓰므로 **5번째 공유 지점이 된다** `(+8/31)`. B가 이미
`OrderUI`·`ResultPanelUI`를 쥐고 있으니 2차 시작할 때 B가 만들고 A가 쓴다.

> 뒤집히는 조건: **게임패드 지원이 들어오면.** 아래 참고.

## 8. 게임패드가 들어오면 설계가 통째로 바뀐다

MdCalling은 인벤토리를 `InventoryState : PlayerStateBase`로 만들었다. 이유는
잠금이 아니라 **입력 라우팅**이다. `IPlayerState`가 버튼 핸들러 18개를 갖고, 같은
버튼이 상태마다 완전히 다른 뜻이 된다.

| 버튼 | Walking | Inventory | Dialogue |
|---|---|---|---|
| A | 상호작용 | 집기 / 놓기 | 다음 대사 |
| B | — | 드래그 취소 | — |
| LB·RB | — | 아이템 90도 회전 | — |
| DPad | — | 그리드 네비게이션 | — |

마우스만이면 이게 필요 없다. **UI가 클릭을 알아서 먹기 때문이다** — `EventSystem`이
레이캐스트를 가로채므로 게이트 하나면 된다. 패드는 A 버튼이 어디로 갈지 아무도
안 정해주므로 명시적 라우터가 필요하다.

MdCalling `ThirdPerson.cs`에 전환이 두 종류인 것도 이 때문이다.

- `ChangeState()` — 갈아탄다 (걷기 → 자전거). `Exit()` 후 교체
- `InterruptState()` — 얹는다 (무엇이든 → 인벤토리). `Suspend()` 후 스택에 쌓고,
  닫을 때 꺼내서 `Resume()`

즉 MdCalling의 상태 스택과 여기 `UIStack`은 **같은 물건을 다른 층에 둔 것**이다.

> 뒤집히는 조건: 팀이 패드 지원을 하기로 하면 결정 7을 버리고 MdCalling 방식으로
> 간다. 전환 비용은 낮다 — `PlayerController`의 `switch`를 상태 클래스로 쪼개는
> 국소 작업이고, `IInteractable`·`DayPhase` 같은 A↔B 계약은 건드리지 않는다.
> **1차 시작 전에 팀에 확인할 것.**

## 9. 서빙 직원은 통째로 A가 갖는다 `(+8/31)`

기획에 서빙 AI 직원이 들어왔다(2026-08-31). 손님·테이블이 B 소유라 직원도 B처럼
보이지만, **직원이 실제로 하는 일의 대부분은 A의 뼈대**다.

| 직원이 하는 일 | 이미 있는 것 |
|---|---|
| 목적지로 걸어간다 (NavMesh) | `PlayerController`의 이동 |
| 도착을 판정한다 | `TickArrival()` |
| 무엇을 어디로 옮길지 정한다 | **없다. B가 알려줘야 한다** |

B가 가져가면 NavMesh 이동·도착 판정이 **두 벌**이 된다. 도착 임계값 같은 값이 서로
달라지고, 3주차에 합칠 때 갈린다. 부하도 안 맞는다 — 미니게임이 B에 있는 상태에서
직원까지 B면 3주에 못 끝낸다.

그래서 **직원의 다리는 A, 머리는 B**로 가른다. B는 `IServeBoard`로 "무엇을 어디로"만
알려주고(공유 지점 4), A는 `Table`·`Customer`·`Order`를 모른 채 Vector3 둘만 보고 옮긴다.

기획 확정 사항 셋이 계약을 단순한 쪽으로 끌어당겼다.

- **플레이어는 서빙하지 않는다** → `IServeBoard`의 소비자가 직원 하나뿐이다.
  둘이 같은 작업을 집는 경쟁 상태를 생각할 필요가 없다
- **1차는 1명 고정** (고용에 드는 재화가 2차라서) → 씬에 하나 놓으면 끝
- **배달 실패가 없다** → `Fail` 경로도 되돌리기도 없다. `TryTake`/`Complete` 둘로 닫힌다

> 뒤집히는 조건: **직원이 무엇을 할지 정하는 판단이 주문 데이터에 깊게 의존하게 되면.**
> 지금은 "대기 목록에서 하나 집는다"뿐이라 A가 데이터를 몰라도 된다. 우선순위(오래
> 기다린 손님 먼저)나 동선 최적화가 들어오면 그 판단은 B로 넘긴다 — A는 여전히 다리만
> 갖는다. 계약을 `TryTake`에서 "B가 정해서 밀어주는" 방향으로 뒤집는 게 그때의 작업이다.

## 10. 직원은 `IInteractor`를 구현하지 않는다 `(+8/31)`

`IInteractor` 주석에 "지금은 플레이어 하나뿐이지만 인터페이스로 노출한다"고 써둔 게
있어서, 직원이 그 두 번째 구현체처럼 보인다. **아니다.** 두 군데서 터진다.

1. **`IInteractor.Warehouse`** — 직원은 창고를 쓸 일이 없는데 내놔야 한다. 내주면
   직원이 요리대에서 재료를 차감할 수 있는 상태가 된다
2. **`Table.Interact(actor)`에 두 경로가 겹친다** — "플레이어가 클릭해서 왔다"와
   "직원이 배달하러 왔다"가 같은 함수로 들어온다. 그때부터 B가 actor 타입을 검사하기
   시작하고, `IInteractor`를 인터페이스로 만든 이유가 사라진다

`IInteractor`는 **"클릭 상호작용을 거는 주체"의 계약**이다. 직원은 클릭하지도, 클릭
당하지도 않는다. 직원에게 필요한 건 "목적지까지 걸어가고 도착하면 알려줘" 하나뿐이다.

그래서 이동만 컴포넌트로 뽑아 공유한다. `PlayerController`와 `ServingStaff`가 둘 다 쓴다.

```csharp
// Assets/Scripts/Core/AgentMover.cs   (A 전용, B와 협의 불필요)
[RequireComponent(typeof(NavMeshAgent))]
public class AgentMover : MonoBehaviour {
    public bool IsMoving { get; }
    public void GoTo(Vector3 destination, Action onArrived);
    public void Stop();
}
```

`AgentMover`는 A 내부 물건이라 계약이 아니다. 마음대로 고쳐도 B는 모른다.

> 뒤집히는 조건: **직원이 상호작용 오브젝트를 실제로 조작해야 하면.** 예를 들어 직원이
> 요리대를 직접 켜거나 밭을 수확하게 되면 그때는 `IInteractor`가 맞다. 그 시점엔
> `Warehouse`를 인터페이스에서 빼서 별도로 가르는 작업이 먼저다.

## 11. 미니게임 입력은 B가 자기 에셋을 갖는다 `(+8/31)`

**이 결정은 Unity 관례와 반대다.** 근거를 안 남기면 나중에 봤을 때 이상해 보인다.

관례는 **`InputActionAsset` 하나에 액션 맵 여러 개**다. 맵은 상황(context) 단위라
`Player` / `Minigame` / `UI` 로 나누고 한 번에 하나만 켠다. 같은 키가 맵마다 다른 뜻이
될 수 있고, 리바인딩 저장이 에셋 단위라 설정 UI를 한 군데만 보면 된다.

그런데 여기서는 갈라 놓는다.

```
Assets/Scripts/Player/PlayerInputAction.inputactions   (A)
        ↓
PlayerInputReader (A)  ─ MoveAxis ─────────▶ PlayerController (A)
                       └ PointerPosition ──▶ ClickSelector (A)
                         ClickPressed

Assets/Scripts/Shop/MinigameInput.inputactions         (B)
        ↓
MinigameInputReader (B) ─ HitPressed ──────▶ CookingMiniGame (B)
```

### 왜 갈랐나 — 기술이 아니라 협업 조건 때문이다

`.inputactions` 는 **JSON**이다. 2인이 3주 동안 서로의 파일을 안 열고 짜다가 3주차에
처음 합치는 구조에서 이걸 공유하면, **머지 충돌을 JSON으로 손으로 푸는 일**이 생긴다.
씬 파일과 같은 종류의 사고다.

합쳐 쓰면 공유 지점이 **하나 더 는다.** B가 `_actions.Minigame.Hit` 을 읽으려면
`PlayerInputReader`(A 파일)에 프로퍼티가 있어야 한다.

```csharp
public bool HitPressed => _actions.Minigame.Hit.WasPressedThisFrame();   // A가 추가해야 함
```

1차는 미니게임 1종이고 입력이 한두 개다. **리바인딩이 두 벌로 갈리는 비용보다
충돌 비용이 크다.**

### `PlayerController` 는 이 문제와 무관하다

"미니게임에 플레이어 입력이 들어가니 `PlayerController` 를 건드려야 하지 않나"는
자연스러운 오해다. 아니다 — **입력을 읽는 건 `PlayerInputReader` 고
`PlayerController` 는 그 소비자 중 하나일 뿐이다**(`ClickSelector` 도 같은 자격).
그래서 압력이 걸리는 파일은 `PlayerController` 가 아니라 `PlayerInputReader` 다.

### 새 계약은 필요 없다

미니게임 중 플레이어를 멈추는 건 **첫날 확정한 `BeginBusy()` / `EndBusy()`** 가 한다.
`PlayerController.Update()` 의 `if (_busyHeld) return;` 한 줄이 전부다.
B는 `IInteractor` 만 보면 되고 A의 구체 타입을 모른다.

⚠️ 알려진 구멍 — **`ClickSelector` 의 hover 는 busy 중에도 돈다.** 클릭은
`GoInteract` 가 `_busyHeld` 로 거르지만 마우스를 올리면 하이라이트가 켜진다.
지금은 로그뿐이라 티가 안 나고, 아웃라인을 붙이면 보인다. A가 게이트 한 줄을 넣으면 된다.

⚠️ 또 하나 — `EndBusy()` 를 B가 빠뜨리거나 미니게임이 예외로 죽으면 **플레이어가
영구히 잠긴다.** 움직이지도 클릭하지도 못하고 에러도 안 뜬다. 실제로 그 일이 생기면
`PlayerController` 쪽에 타임아웃(예: 60초 넘게 busy면 경고 로그 + 강제 해제)을 넣는다.
A 내부 한 줄이라 나중에 넣어도 B는 모른다.

### B에게 전할 한 줄

> 미니게임 입력은 `Assets/Scripts/Shop/MinigameInput.inputactions` 를 새로 만들어 쓴다.
> A의 `PlayerInputAction` 은 열지 마라. 플레이어를 멈추는 건
> `actor.BeginBusy()` / `actor.EndBusy()` 로 한다.

이걸 안 정해두면 **B는 당연히 A의 에셋을 열어서 맵을 추가한다.** 그게 Unity에서
자연스러운 선택이라서다.

> 뒤집히는 조건: **키 설정 UI나 게임패드가 들어오면** 에셋 하나로 합친다. 그때는
> 리바인딩 저장이 에셋 단위라 갈려 있으면 설정 화면이 두 벌이 된다. 합치는 비용은
> 낮다 — 맵을 통째로 복사해 붙이고 `PlayerInputReader` 에 프로퍼티를 옮기면 된다.
> 그 시점에 `PlayerInputReader` 가 5번째 공유 지점이 된다.
