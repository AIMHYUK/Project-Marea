**표기** — `(+8/31)` 처럼 붙은 것은 **그날 추가·변경된 항목**이다.
날짜가 없는 줄은 최초 작성분(8/28)이다. 갱신할 때마다 바뀐 자리에 날짜를 붙인다.

플레이 구조: 재료 준비 → 영업 시작 → 주문 → 요리 → 판매 → 정산 → 성장

가르는 기준은 기능 개수가 아니라 **의존성**이다. 같은 뼈대를 쓰는 것끼리 묶고,
경계를 넘는 지점만 계약으로 못박는다.

## 루프에서 어디가 누구 것인가

| 재료 준비 | 영업 시작 | 주문 | 요리 | 판매 | 정산 | 성장 |
|---|---|---|---|---|---|---|
| **A** | B | B | B | B (전달만 A +8/31) | B | (2차) |

영업 시간 전체가 B, 그 앞뒤의 준비와 성장이 A다. 인수인계는 두 곳뿐이다.

1. **준비 → 영업** — A의 창고가 B의 요리에 재료를 대준다
2. **정산 → 준비** — B가 하루를 끝내면 A의 밭·재화가 다음 날을 준비한다

## 왜 이렇게 갈랐나

- **상호작용은 통째로 A** — 밭·요리대·테이블이 전부 같은 뼈대(클릭 → 이동 → 도착 실행)를
  쓴다. 나눠 잡으면 100% 충돌한다. A가 인터페이스만 먼저 커밋하고 B는 구현만 한다.
- **요리는 쪼개지 않음** — 재료 확인 → 미니게임 → 판정 → 가격이 한 호흡이다. 중간에서
  자르면 판정 결과를 넘기는 콜백이 하나 더 생기고 그 경계에서 버그가 난다.
- **개수 대신 총량으로** — A 16 / B 19다. 서빙 직원이 A로 오면서 좁혀졌다 `(+8/31)`.
  재화·농사 확장도 전부 A로 온다. 차수마다 딱 맞추려고 기능을 반토막 내지 않는다.
- **매출·정산은 B** — 주문 데이터를 쥔 쪽이 계산까지 하는 게 자연스럽고, 판정 등급만
  가격에 곱하면 되므로 경계가 생기지 않는다.
- **서빙 직원은 통째로 A** `(+8/31)` — 직원이 하는 일의 대부분이 NavMesh 이동과
  도착 판정이라 플레이어와 같은 뼈대다. B가 가져가면 이동 코드가 두 벌이 되고 3주차에 갈린다.
  미니게임까지 진 B가 직원을 더 받으면 3주에 못 끝내는 문제도 있다.
  B는 "무엇을 어디로 옮길지"만 알려준다.

## 공유 지점은 네 개

> `(+8/31)` 기획에 서빙 AI 직원이 들어오면서 네 번째가 늘었다. 셋까지는 8/28에 정한 것이다.

이 넷만 **첫날에** 껍데기까지 커밋해두면 그다음부터 서로의 파일을 열 일이 없다.
하나는 같이 만들고, **둘은 A가 주고**, 하나는 B가 준다 `(+8/31)`.

### 1. 재료·메뉴 데이터 — 같이 확정

```csharp
[CreateAssetMenu(menuName = "Marea/Ingredient")]
public class IngredientData : ScriptableObject {
    public int Id { get; }
    public string DisplayName { get; }
    public Sprite Icon { get; }
}

[Serializable]
public struct RecipeEntry { public IngredientData ingredient; public int count; }

[CreateAssetMenu(menuName = "Marea/Menu")]
public class MenuData : ScriptableObject {
    public int Id { get; }
    public string DisplayName { get; }
    public IReadOnlyList<RecipeEntry> Recipe { get; }
    public int BasePrice { get; }   // 판정 배율을 여기 곱한다
}
```

에셋 파일도 첫날에 3~4종 만들어 커밋한다. 빈 껍데기라도 있어야 A는 창고를,
B는 주문을 붙일 수 있다.

### 2. 상호작용 · 창고 — A가 주고 B가 쓴다

```csharp
public interface IInteractable {
    Vector3 InteractPoint { get; }              // 캐릭터가 설 위치
    bool CanInteract(IInteractor actor);        // 선택 가능 여부
    void Interact(IInteractor actor);           // 도착 후 호출됨
}
// → B가 CookingStation, Table 에 구현 (InteractableBase 상속)

public interface IInteractor {
    Transform Transform { get; }
    Warehouse Warehouse { get; }
    void BeginBusy();   // 상호작용이 여러 프레임 이어질 때 (미니게임)
    void EndBusy();
}

public class Warehouse : MonoBehaviour {
    public bool Has(MenuData menu);
    public bool Consume(MenuData menu);
    public void Add(IngredientData ingredient, int count);
}
```

- **`IInteractable`을 직접 구현하지 말고 반드시 `InteractableBase`를 상속한다** `(+8/31)`.
  `ClickSelector`가 base 타입으로 대상을 찾기 때문에, 직접 구현하면 **클릭이 아예 안 잡힌다.**
  에러가 안 나고 그냥 반응이 없어서 원인 찾는 데 오래 걸린다.
- B는 이동이 어떻게 되는지 알 필요가 없다. `Interact()`가 불렸다면 캐릭터는 이미 도착해 있다.
- B는 `PlayerController` 구체 타입을 참조하지 않는다. `IInteractor`만 본다.
- **미니게임처럼 여러 프레임 이어지는 상호작용은 `BeginBusy()` / `EndBusy()`로 감싼다.**
  안 감싸면 미니게임 중에 WASD로 걸어나갈 수 있다. `EndBusy()`를 빠뜨리면 플레이어가
  영구히 잠기니 미니게임 완료 콜백에서 반드시 부른다.

### 3. 게임 상태 — B가 주고 A는 읽기만

```csharp
public enum DayPhase { Preparing, Open, Closing }

public class GameManager : MonoBehaviour {
    public static GameManager Instance { get; private set; }
    public DayPhase Phase { get; private set; }
    public event Action<DayPhase> OnPhaseChanged;   // A·UI가 구독
    public void SetPhase(DayPhase next);            // B만 호출
}
```

A는 `Phase`를 읽어 입력을 잠그기만 한다. 절대 `SetPhase()`를 부르지 않는다.

### 4. 서빙 작업 — A가 주고 B가 쓴다 `(+8/31)`

> `(+8/31)` **방향이 뒤집혔다.** 처음엔 `IServeBoard`를 B가 구현하는 것으로 적었으나,
> 인터페이스가 값을 못 한다고 판단해 **A 소유 구체 클래스**로 바꿨다.
> 구현이 하나뿐이고 B가 구현할 물건도 아니다 — `Warehouse`와 같은 패턴이다.
> 아래가 확정본이다.

B는 "음식이 완성됐다"만 알려주고, A의 직원이 걸어서 옮긴다.

```csharp
public struct ServeTask {
    public Vector3 PickupPoint;    // 어디서 받나 (요리대)
    public Vector3 DeliverPoint;   // 어디로 (테이블 옆)
    public Sprite  FoodIcon;       // 직원이 들고 갈 그림
}

public class ServeBoard : MonoBehaviour {
    public void Post(Vector3 pickup, Vector3 deliver, Sprite icon);  // B가 부른다
    internal bool TryTake(out ServeTask task);                       // 직원이 꺼낸다
    internal void Complete(ServeTask task);                          // 배달 끝. 매출은 여기서
}
```

- **B가 할 일은 `Post()` 한 줄이다.** 음식이 완성되면 픽업 좌표·배달 좌표·아이콘을 넘긴다.
- **A는 `Table`도 `Customer`도 `Order`도 모른다.** Vector3 둘과 아이콘 하나만 안다.
  B는 직원이 어떻게 걸어가는지 모른다.
- **board는 큐다** `(+8/31)`. 직원보다 음식이 빨리 나오면 여기 쌓인다.
  직원이 유휴일 때만 하나씩 꺼내가므로, 직원이 여러 명이 돼도 같은 음식을 둘이 집지 않는다.
- ⚠️ `internal` 은 실제로 막아주지 않는다. asmdef가 없어 A·B가 같은 어셈블리다.
  "직원만 쓰는 것"이라는 의도 표시일 뿐이다.
- 배달 실패는 **없다**(기획 확정). 그래서 `Fail` 경로도, 되돌리기도 없다.
  두 함수로 계약이 닫힌다.
- **플레이어는 서빙하지 않는다**(기획 확정). `ServeBoard`에서 꺼내가는 건 직원 하나뿐이라
  둘이 같은 작업을 집는 경쟁 상태를 생각하지 않아도 된다.

⚠️ **직원에게 `IInteractor`를 구현시키지 않는다.** 두 군데서 터진다.
하나는 `IInteractor.Warehouse` — 직원은 창고를 쓸 일이 없는데 내놔야 한다.
다른 하나는 B의 `Table.Interact(actor)`에 "플레이어가 클릭해서 온 것"과
"직원이 배달하러 온 것"이 **같은 경로로 들어온다**는 것이다. 그때부터 B가 actor 타입을
검사하기 시작하고, 인터페이스를 만든 이유가 사라진다.
직원은 클릭 경로를 안 탄다 — `AgentMover`만 플레이어와 공유한다.

## 3주 진행

첫날에 공유 지점 3개를 먼저 커밋하고 시작한다. 그 뒤로는 3주차 마지막에 처음 합친다.

| | A | B | 끝나면 |
|---|---|---|---|
| **1주차** 뼈대 | 이동·카메라·클릭 감지, `IInteractable`·`Warehouse` 껍데기 커밋, **`AgentMover` 추출 · `ServeBoard` 껍데기 커밋** `(+8/31)` | `DayPhase` 껍데기 커밋, 데이터 에셋 작성, 상태 전환 + 손님 스폰·착석 | 캐릭터가 걷고 손님이 앉는다 |
| **2주차** 살 붙이기 | 창고 실제 구현, 밭 성장·완료 아이콘·수확, **직원 픽업→배달 왕복** `(+8/31)` | 주문 생성·말풍선 UI, 요리대 상호작용 + 메뉴 선택, 완성 시 **`ServeBoard.Post()` 호출** `(+8/31)` | 수확되고 주문이 뜬다 |
| **3주차** 연결 | 재료 차감 연동, **직원·미니게임 동시 구동 확인** `(+8/31)`, 예외 처리·다듬기 | 미니게임·판정, 매출 계산, 정산 UI·초기화 | 하루 루프가 끝까지 돈다 |
